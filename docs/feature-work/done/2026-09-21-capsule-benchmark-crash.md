# FMS-Issue-021: capsule benchmark crash investigation

Closed on 2026-09-21 as **not reproducible on current revision `da6b6f1`** after
a bounded investigation. The original cause remains unattributed; this is not
a claim that a runtime or geometry defect was found and fixed. Reopen with new
failure evidence rather than continuing speculative settings changes.

## Original observation

On 2026-09-21, `CenteredCapsuleConvexBenchmarks.CornerMiss` threw a managed
`NullReferenceException` after pilot and warmup, at the first actual measurement
of the fourth case in an out-of-process DefaultJob run. That child exited `-1`,
produced no workload results, and the launcher correctly returned `1`.
The failed capture is excluded from performance evidence.

Input: polygon `(-1,-1),(0,-1),(0,0),(-1,0)`, capsule center `(3,4)`, Forward
axis, zero axis length, radius `5 - Fixed64.MinIncrement`, and zero polygon
origin/rotation. Expected classification: separated.

Environment: Windows 11 build 26200.9457, Intel i7-9700K, SDK 10.0.302,
.NET 8.0.29 x64 RyuJIT, concurrent workstation GC, BenchmarkDotNet 0.15.8.

The source was `8e03b14` plus the intermediate FMS-Issue-020 exact-axis fix,
before per-query rotation-frame reuse. Its edge loop called
`GetRelativePointNumerators(Vector2d.Zero, convexRotation, vertexOffset,
Vector2d.Zero, out x, out y)` for each endpoint. The final #20 implementation
calls `GetRotatedOffset` with a retained rotation frame directly. That change
does not establish why the crash happened or prove that it repaired a crash.

## Bounded investigation

The source audit found value-type operands and integer arithmetic at the
reported helper, with no nullable object dereference that explains the NRE.
This is insufficient to attribute the failure to library code, runtime/JIT,
BenchmarkDotNet, or the environment. There is no native fault context for the
original failure, and its intermediate source is not a committed replay target.

Fresh checks use committed `da6b6f1` on the same environment. The benchmark
project builds in Release with zero warnings/errors. No runtime code, GC/JIT
settings, dependencies, or benchmark behavior were changed for this investigation.

The first-chance access-violation collector was revalidated using a separate
.NET 8 control program:

```csharp
[System.Runtime.CompilerServices.MethodImpl(
    System.Runtime.CompilerServices.MethodImplOptions.NoInlining)]
static int Touch(object value) => value.GetHashCode();

try { System.Console.WriteLine(Touch(null)); }
catch (System.NullReferenceException)
{
    System.Console.WriteLine("CONTROL_CAUGHT_NULL_REFERENCE");
}
```

CDB captured native `c0000005` null reads in the control, wrote dumps, and
the program subsequently printed its caught-exception marker and exited zero.
This validates collection before managed exception handling; an unhandled-only
collector can miss failures that BenchmarkDotNet catches.

Fresh replay results:

| Check | Completed launches | Actual measurement iterations | Result |
| --- | ---: | ---: | --- |
| `CornerMiss`, CDB following children with first-chance AV collection | 3/3 | 45 | All children exited zero; no captured AV, NRE, or missing results; CDB exited zero |
| Full five-case alias, without debugger | 5/5 | 75 | All children and launcher exited zero; no NRE or missing results |

The benchmark setup checks expected classifications, including the corner
miss, and validates the corrected side witness. These runs provide diagnostic
evidence, not performance comparisons. They supplement the two successful
full four-case runs after #20 and the successful five-case run after #22.

There is no current reproducer, native fault context, or source-level defect
that supports a targeted correction. The active tracker entry is removed.
Current passes do not explain the intermediate-source failure or exclude an
intermittent problem; that limit is why recurrence evidence below is retained.

## Reproduction and recurrence evidence

From the repository root:

```sh
dotnet build tests/FixedMathSharp.Benchmarks/FixedMathSharp.Benchmarks.csproj -c Release -f net8.0
dotnet tests/FixedMathSharp.Benchmarks/bin/Release/net8.0/FixedMathSharp.Benchmarks.dll centered-capsule-convex --filter "*CornerMiss*" --launchCount 3 --exporters json
dotnet tests/FixedMathSharp.Benchmarks/bin/Release/net8.0/FixedMathSharp.Benchmarks.dll centered-capsule-convex --exporters json
```

On Windows, CDB can follow child processes with `-o`. A command file loaded
with `-cf` can capture first-chance native faults before continuing normal
exception handling. Create the output directory first, and run from the repo
root so this relative dump path resolves:

```text
sxi ibp
sxe -c ".echo ISSUE021_FIRST_CHANCE_AV; .dump /ma /u artifacts/fms-issue021/fault.dmp; .exr -1; r; k; gn" av
g
```

Use `-G` to continue final process exit and supply `dotnet` plus the benchmark
command as the debuggee. Validate the control first. Check benchmark child
exits and workload results separately from the debugger's own exit code.

On recurrence, record the source commit and local diff, runtime/SDK/OS versions,
exact command, case and launch number, child/launcher exits, and managed stack.
Prefer a first-chance native dump with exception code/address, registers and
stack, plus the matching binaries/PDBs. Preserve the diagnosis in a new issue;
temporary dumps and logs are supplemental and must not be its only evidence.
